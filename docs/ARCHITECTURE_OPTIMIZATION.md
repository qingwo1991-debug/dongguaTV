# 架构优化评估：能否 Go 化？如何达到极速响应/播放/首页/搜索

> 结论先行：**不建议整站 Go 重写**（风险远大于收益）；推荐“**Node 保核心（JS 扩展引擎）+ 选择性 Go 化（流式媒体代理）** + **零重写的缓存/并行/聚合级优化**”三条腿并进。

---

## 一、为什么“Go 化”不是首要选择

### 1. 系统核心是“第三方 JS 扩展脚本”，几乎无法 Go 化
本项目的 XPTV/csp_* 源本质是**远程下发的 JS 脚本**，在服务端用 Node 的 `vm` 沙箱执行：

- 脚本依赖 `CryptoJS`（AES 解密）、`Cheerio`（DOM 解析）、`$fetch/$get/$post`、`iconv-lite`（gb2312）等大量 JS 生态；
- 一旦 Go 化，要么：
  - 用 `goja`（纯 Go JS 引擎）——它无法忠实跑绝大多数真实 csp 脚本（CryptoJS/Cheerio/编码都需逐一手写移植），真实源极易跑挂；
  - 或者在 Go 旁边挂一个 Node sidecar 执行脚本——等于没迁移，还多了进程通信复杂度。

**结论**：扩展引擎必须留在 JS 生态。全量 Go 化 = 为 0.1% 的性能收益扛 100% 的源兼容性风险。

### 2. 实测瓶颈在上游网络 + 缓存，不在 Node 本身
本部署采样（2026-09 实测）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 详情（含卡片/结构） | 0.02–10s | 主要被**上游 getTracks** 拖慢，本机几乎白等 |
| 首帧 manifest（预热前） | 1.4–2.6s | 上游清单拉取 |
| 首帧（预热 + 缓存后） | **0.02–0.05s** | 我们已优化的成果 |
| 切集 resolve+清单（预热后） | **0.03s** | 全命中缓存 |
| Node 本机开销 | <ms 级 | 纯 I/O，事件循环根本不吃 CPU |

换 Go 不会降低上游延迟，也不会让缓存变快——**瓶颈已经被“预热 + 缓存 + keep-alive + 并发”解决**。

### 3. 什么时候才真正值得 Go
- 并发吞吐成为墙（如同时数百上千路播放/搜索）；
- 需要**边缘/冷启动极低内存**、多实例部署、容器化扩展；
- 媒体下载/转码类 CPU 密集场景。

单机家/小型部署下，这些场景不成立，Go 的优势发挥不出来。

## 二、推荐架构：局部 Go 化（风险可控、收益聚焦）

保持 Node 处理“业务 + JS 扩展”，把“高带宽、长连接、高吞吐”的**流式媒体代理**让 Go 来抗：

```
浏览器
  │  :3000 (Go 网关层：静态资源 / 媒体流)
  ├── /api/ext-hls-proxy, /api/m3u8-proxy, /api/tmdb-image, /static
  │        → Go 流式转发（TCP keep-alive、HTTP/2、pipe 零拷贝、无 GC 抖动）
  └── :3001 (Node 业务层)
         /api/ext/cards /api/ext/resolve-play /api/detail /api/search /api/tmdb-proxy
         （JS vm 扩展引擎 + 预热/缓存）
```

收益：
- 播放/流媒体的**带宽与连接稳定性**由 Go 兜底（大并发、长连接无 GC 停顿）；
- 扩展引擎零风险，源兼容不动；
- 可用 nginx 合并端口，或 Go 直接在 3000 上反代 3001 的 Node。

> 若短期内不想引入 Go：流式代理留在 Node 亦可（当前已加 keep-alive 连接池），性能在家庭规模足够了。

## 三、零重写也能“极速”的优先级清单（按 P0→P3 落地）

### P0 · 响应速度
1. **首页聚合一个接口**：新增 `/api/home` 一次返回 hero + 前 6 行数据（现在各 tab 逐行请求）。前端改成一次拉取、渐进渲染 → 首屏往返从 N 次降到 1 次。
2. **磁盘化播放缓存**：把内存 `extPlayinfoCache / extManifestCache` 落到磁盘（SQLite/文件），**重启不冷**，配合“容器启动即预热各源首页”。
3. **重启预热**：服务启动后立即并行预热 21 源首页结构 + 首卡媒体（延续现有 cards 预热逻辑）。

### P1 · 播放
1. 已落地：卡片期结构+媒体+清单预热、详情期 11 集深度预解析、keep-alive 连接池、清单/直链双层缓存、inflight 去重、直连→代理无缝回退。
2. 追加：播放器**分片级预取**（当前集尾返回 1-2 段）、有条件的 Low-Latency HLS（部分源可用则开）。

### P2 · 搜索
1. **搜索结果缓存**（约 3 天）+ 命中即秒回；慢源**熔断/超时降级**，避免全等慢源；
2. **部分流式返回**:前 3 个最快源先返回渲染，其余并行补齐（前端 300–500ms 先用同一亚筹显）。

### P3 · 首页展示（“科学展示”）
- Hero 用 TMDB 热门 + 自适应后拨（已有）;
- 21 栏按 `健康度/热度/最近可播` 排序；统计各源成功率自适应前端降级；
- 图片走本站缓存代理（`/api/tmdb-image`, 扩展源图已做白名单+解密）。

## 四、量化验收指标（改完按此验收）
- 缓存命中后「点击卡片→首帧画面」≤ **500ms**（当前清单阶段已 ≤50ms，剩余为前端/DPlayer 起播）
- 「切换剧集/连播」≤ **300ms**（当前已 0.03s）
- 「首页打开」≤ **1s 出首屏行**
- 「搜索」首屏 ≤ 500ms（前 3 源），全量 ≤ 2s（含熔断兜底）
- 服务端 CPU 峰值 < 50%（单核）
